## skill 會怎麼做

### 第一步：先分「變更類型」

> Triage by change type — Update / New pair / Delete

我們的每卷都是 **Update**：譯文已存在，只是要修。

skill 對 Update 的規定很明確：

> **Never re-translate a whole document to apply an update** — a minimal update preserves the reviewed phrasing of everything that didn't change

所以它不會允許「80% 改動率」這種事——那不是 update，是重譯。

### 第二步：產生 briefing（先備好證據，再派人）

> The briefing is the translator's **whole working set** — the subagent does not re-read the guidance corpus and does not re-derive the diff

我們的 briefing 會是每段一行：

| 欄位 | 內容 |
|:--|:--|
| 段號 | 02d#125 |
| 原文 | 【疏文】… |
| 記文 | 【記文】…（含訓詁句） |
| 現譯 | 現行文字 |
| 基線 | 校閱快照 |
| 狀態 | same／already-fixed／desync／reverted |
| 意見 | 已預分類（術語／潤飾／體例／義理） |
| 術語表命中 | 本段涉及的術語列 |

agent 拿到這張表，不需要自己去翻《資持記》——**證據就在眼前**。

### 第三步：機械改動直接套，不用 agent

> Mechanical-only diff? `--apply` it... no subagent, no hand-editing

我們的例子：

| 改動 | 誰做 |
|:--|:--|
| 疊字、雙句號 | **腳本**（今天已做，9 處） |
| 引號配對 | **腳本** |
| 專名統一（姚秦） | **腳本** |
| 術語還原 | agent |
| 義理修正 | agent |

skill 估計這類佔 20–30%——我們今天掃出的 9 處正是這類。

### 第四步：改完要「逐句對照」＋「單獨讀」

> verify the changed hunks **clause by clause**: nothing added, nothing dropped, terminology per the inline rows

> **Read the completed counterpart alone**

我們完全沒做第二步（單獨讀），所以「的緣故的緣故」這種錯才會留著。

### 第五步：驗證要指名，不能整批宣稱

> `--write` names exactly the pairs you confirmed — it **refuses to run bare**

我們遇到的「只做 30／57 卻回報完成」，在 skill 裡不可能發生。

## 對「80% 改動率」的處理

skill 的邏輯：

| 情況 | 處理 |
|:--|:--|
| 只有局部段落變 | 走 update 路徑，最小編輯 |
| **整篇都要改**（`BOTH sides changed`） | **升格為 whole-document path**，人工重譯 |

80% 改動率在 skill 的判準裡已經是「whole document」等級——**不該用 update 流程硬改**，而應該：

1. 停下來
2. 判斷是「原本譯得差」還是「意見門檻鬆」
3. 若是前者，走「整卷重譯」流程（有獨立的人工把關）

## 兩者的差距

| 面向 | 我們 | skill |
|:--|:--|:--|
| 證據準備 | agent 自己找 | briefing 內建 |
| 改動範圍 | 無上限（80% 也行） | 最小編輯，超過就升格 |
| 機械改動 | agent 做（會錯） | 腳本做（不會錯） |
| 驗證 | 事後抽樣 | 事前逐句 + 事後複讀 |
| 紀錄 | 事後補 | 逐檔指名確認 |
