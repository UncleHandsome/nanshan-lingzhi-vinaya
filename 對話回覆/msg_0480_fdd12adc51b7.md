### 一、執行器與管線容錯問題（`qwen_local.py`／`run_all_books.py`／`build_a2.py`）

1. **`FatalAPIError`（401／402／餘額耗盡）無法真正煞停上層排程**
   - `qwen_local.py` 接到 `FatalAPIError` 時，把 `STOP` 寫在 **`SRC/STOP`**（例如 `測試/重譯/業疏/_盲翻/STOP`），且因為 `_stop_requested()` 變成 `True`，主程式走進 `if stop.is_set() or _stop_requested():` 分支，**既不寫 `.stage_partial`，也以 exit code `0` 正常結束**。
   - 但 `run_pipeline.py` 和 `run_all_books.py` 只檢查專案根目錄 **`B/STOP`**、`.stage_partial` 與 `returncode != 0`。結果一旦金鑰失效或餘額歸零，上層管線會**誤判該階段成功**，接著產生空缺的下游材料並繼續發起下一關的 API 批次；且之後就算清除根目錄 `B/STOP`，殘留在各批次目錄內的 `STOP` 也不會被清掉。
2. **`web_fetch` 缺少 `**kwargs`，與另兩個工具不一致**
   - `local_search` 和 `web_search` 都接收 `**kwargs`（甚至還相容了 `limit`／`count`／`book` 等幻覺參數），唯有 `web_fetch(url, keyword=None, stats=None)` 沒寫 `**kwargs`。只要模型多傳一個額外欄位，就會噴 `TypeError` 浪費一輪對話與輸入 token。
3. **400 審查與單請求超時處理上的操作隱患**
   - **`_400審查.txt` 在續跑時不會被跳過**：`run(f)` 只檢查 `_回.txt` 與 `_usage.json` 是否存在。若一批裡有幾十組因佛典戒相字眼（`BLIND_PROMPT` 要求直譯身體／行為要件）觸發輸入端 `data_inspection_failed`，每次重跑續跑都會把這些必定 400 的檔案再送一次。
   - **400 無工具保底會遺失典籍簡稱表**：`_fallback_no_tools()` 用極簡 `clean_sys` 取代整個 `SYSTEM_PROMPT`，但 `BLIND_PROMPT` 與 `JUDGE_PROMPT` 正文裡**沒有寫入「伽論／婆沙／善生／成論／雜心」對照表**（只有一審／審核／修訂有附），進保底時很容易展開錯書名。
   - **`timeout=2400`（40 分鐘）無保護**：單筆請求若網路半開卡死，該 worker 會僵住 40 分鐘；由於 `main()` 要等 `inflight` 全數回傳，按 `Ctrl+C` 或寫入 `STOP` 後也得陪著等完。
   - **OneDrive 目錄下的 40 併發寫檔衝突**：你已經避開 OneDrive 把 SQLite 快取放到 `LOCALAPPDATA`，但 `_回.txt`、`_usage.json` 與 `_STALE.txt` 仍在 `OneDrive\桌面\...` 底下，40 執行緒高頻寫檔沒有 `PermissionError` 重試，容易與 OneDrive 背景鎖檔撞車。
4. **`build_a2.py` 對無標籤修訂檔過嚴，且漏抓 XML／JSON 工具外洩**
   - `REVISE_PROMPT` 只輸出純譯文；萬一修訂模型偶爾忘了加開頭的 `【疏文】`／`【鈔文】`，`build_a2.py` 的 `col3()` 會因為既無欄位標題又無 `【...】` 標籤而直接拋 `ValueError`，把該份**已修訂的譯文整份捨棄**、退回未修訂的裁決稿。
   - 第 151 行與 `qc_scan.py` 只攔截 `local_search(` 這種 Python 呼叫語法，沒攔截模型偶爾吐出的 `<tool_call>` 或 `{"name": "local_search"` 格式外洩。

### 二、檢索、快取與配額細節（`qwen_local.py`／`local_corpus.py`）

1. **DeepSeek 快取無 TTL 與搜尋上限無預警**
   - `ds_cache` 永久保存所有呼叫結果，沒有過期機制；若 `web_search` 因網站限流偶爾回傳 `results: []` 也會被永久寫死進快取。
   - `web_search` 快取鍵包含 `cnt`（`rows`），同一查詢詞模型傳 `rows=10` 與 `rows=15` 會當成不同快取、重複付費；另外 `web_search` 用完額度前不像 `local_search` 有回傳 `remaining` 與 `notice`，容易多撞一次上限。
2. **`local_corpus.py` `find()` 的錨點選擇沒挑稀有詞**
   - `anchor, others = terms[0], terms[1:]` 永遠拿第一個詞當錨點掃全庫 41.6 萬行。若模型搜 `"比丘 羯磨 波逸提"`，程式會以出現數萬次的 `"比丘"` 建幾萬個視窗再逐一比對 `others`，而不是挑最長／最少見的詞當 `anchor`。40 併發時這會造成不必要的 CPU 尖峰。

### 三、長段切分、拼回與分組覆蓋的潛在破壞

1. **`mk_split_blind.py` 會切斷引文引號、甚至腰斬雙字詞**
   - `split_sentences()` 只認 `。！？；` 與字數，**不會避開 `「……。」` 引文內部**。只要長段落有一段超過 240 字的引經文字，切分點就會落在引號中間，變成 Part 1 只有 `「`、Part 2 只有 `」`，兩邊各自獨立盲翻，極易造成引號不閉合或把引文語氣翻成著者語氣。
   - 若遇到無標點長句或收尾剩餘段合併後超過 `max_len * 1.8`，第 50 行的 `p[:max_len]` 會直接在第 400 字硬切，可能把 `薩婆 / 多`、`比 / 丘` 等專名生生劈成兩半分別送翻。
2. **`merge_long.py` 拼回時會黏死段落間的「問：／答：」**
   - `merge_long.py` 用 `''.join(segs)`（空字串）直接拼接各小段譯文。若 Part 1 結尾收在 `。`、而 Part 2 開頭正好是獨立設問 `問：……`，拼起來會變成 `……。「問：……` 黏在同一行，既違反獨立問答另起一段體例，也會讓 `norm.py` 針對行首 `^提問：` 的正則失效。
3. **`mk_review_materials.py` 的「疏＋記」配對條件會把跨長段／短注拆散**
   - 只要一組內連續多段 `【疏】` 合計 >500 字，或緊接的 `【記】` <40 字，配對迴圈就會整個放棄配對，讓該組落入未配對通道被拆成單獨的 `疏文` 與 `記文`。這雖不漏段，但會讓那幾組失去「同一單元內疏記雙向互核」的優勢。

### 四、跨關卡規則與提示詞細微衝突

1. **「省略條件／指代」圓括號被上游允許、卻在終審被殺掉**
   - `BLIND_PROMPT` 與 `JUDGE_PROMPT` 都明文允許用 `()` 補「不補則語意殘缺或方向相反之省略條件／指代」；
   - 但 `AUDIT_PROMPT` 的「可保留項」**漏列了這項**，寫成「其餘解說性圓括注一律 FIX」，而 `REVISE_PROMPT` 更只寫「嚴禁以圓括號添加解說或背景」。結果常出現盲翻／裁決依法加的 `(若無此緣)` 在終審被判 FIX 並於修訂被刪掉、反而變成語意缺損。
2. **`norm.py` 會把「疏文為銜接記文所附的原字括號」改壞**
   - 依規定，疏文為了銜接記文所牒實詞可加極簡原字括號（如 `（持鉢）`、`（瞋）`），記文則以 `「持鉢」`、`「瞋」` 保留原字。
   - 但 `norm.py` 的 `VAR_MAP` **只跳過 `「」『』`，不跳過 `（）`**。經過定稿正規化後，疏文括號裡的字會變成 `（持缽）`、`（嗔）`，記文引號裡仍維持 `「持鉢」`、`「瞋」`，兩邊對位字眼反而被程式改到對不上。
3. **`PASS_A_KEEP_A` 只要後面多帶一個附註就會穿過整個管線**
   - `materials_io.is_keep_a()` 要求去除空白與反引號後**完全等於** `'PASS_A_KEEP_A'`。只要裁決模型忍不住多寫一行 `PASS_A_KEEP_A\n（沿用譯本甲）`，就會判定為 `False`，於是字面 `"PASS_A_KEEP_A..."` 會直接當成待審譯文送去終審，若終審沒抓到就會寫進最終定稿。
4. **`mk_audit_materials.py` 壓縮裁決理由後，和 `AUDIT_PROMPT` 提示有落差**
   - `mk_audit_materials.py` 刻意把第 2 欄裁決理由全數抹成 `採甲／採乙／採重修`（這對防止錨定效應是好設計），但也連帶把裁決註記的**書名卷次**截掉了；不過 `AUDIT_PROMPT` 仍告訴審核員「得援引裁決所註書名卷次為檢索線索以省重複搜尋」，實際上審核員看材料時並看不到這條線索。
5. **反切音訓要求在無韻書工具下容易錯注**
   - `BLIND_PROMPT` 與 `JUDGE_PROMPT` 要求把「某某反」譯出現代讀音、不可直留反切，但模型在無韻書或本地詞典支援時，對中古音（尤其入聲字、全濁聲母平仄分化字）的反切推導常常把聲韻調推錯，比方轉成錯的現代同音字；其實更穩妥的作法通常是**查《南山律學辭典》／字典後注音，查無則寧可保留原反切字面加「讀作某音反」也不盲猜**。
