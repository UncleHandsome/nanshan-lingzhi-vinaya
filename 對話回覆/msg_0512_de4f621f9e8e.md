## 一、高風險 Bug（會導致檢索失效、資料損壞或漏段）

### 1. `qwen_local.py` 的 `own_text` 過濾會「誤殺平行原文」（間接導致狂燒網搜與空轉）
在 `qwen_local.py` 的 `local_search` 中，你為了避免搜到「正在翻譯的這一段」，寫了：
```python
if h.get('book') in ('濟緣記', '行宗記', '業疏科', '戒疏科', '行事鈔科', '義鈔科', '尼鈔科', '南山律學辭典'):
    _keep.append(h)
    continue
if any(w and w in _ht for w in _wins):  # _wins 是當前待譯原文每 10 字切出的 20 字滑動視窗
    continue
```
**問題在於**：`四分律`、`隨機羯磨`、`行事鈔`、`戒疏`、`業疏`、`資持記`、`薩婆多毘尼毘婆沙` 等**全部不在那個白名單裡**。
在《業疏》《戒疏》《資持記》中，**大段原文直接引用《四分律》或《隨機羯磨》20 字以上是常態**。當模型想查證某段引文的上下文（例如在《四分律》的前後開遮條件）而呼叫 `local_search` 時：
- 命中的《四分律》或《隨機羯磨》片段（前後各 240 字）一定包含那 20 字引文；
- 結果在 `_LC.find(..., limit=4)` 回傳後，被 `own_text` 過濾器**直接刪光**，變成 `num_found: 0`！
- 接著觸發 `refund`（前 2 次查無免扣額度），模型以為本地查不到，**改呼叫 `web_search` / `web_fetch` 或多跑好幾輪 `xhigh` 思考重試**。這很可能也是你觀察到「28% 查無、但單獨測試 92% 查得到」及 `NO_WEB=1` 輸出暴增的主因之一。

**修法**：只過濾「與當前書別相同」的命中結果（把當前 `book` 傳入 `stats`），或要求重疊率佔待審原文極高比例才過濾，絕對不能把跨書平行引用濾掉。

### 4. `pack_judge.py` 拆回邏輯可能把「錯誤字串」當譯文送進下關
在 `pack_judge.py` 的 `do_split()`：
1. **錯誤字面流入下游**：若第 3 欄解析失敗，程式會把 `'（拆回失敗：缺標籤）'` 或 `'（拆回失敗：缺段）'` 直接寫進 `回覆/ok_key_回.txt`。這串字長度 `>= 1`，`mk_audit_materials.py` 的 `col3_safe` 不會攔截它，會直接把它當「待審譯文」送去終審！

### 6. `qwen_local.py` 在 `RAW_SAVE=1` 時，`_looks_pasted` 可能誤殺正常譯文並中斷整批流程
當 `QWEN_RAW_SAVE=1`（盲翻、修訂都開這個）時：
```python
if _looks_pasted(out, _src_unit(src_text)):
    ...
    return ('pasted', '貼原文')
```
`_looks_pasted` 只比對待審原文與譯文的前 20 個漢字是否有 **≥12 個連續相同**（且原文 >40 字）。
在律典翻譯中，若段落一開頭就是**直接保留的經律引文**（例如 `「若比丘於僧伽藍內……」`）或**長篇科名條列／戒相專名**（如 `第一殺戒、第二盜戒……`），白話譯文開頭前 12 字與原文完全相同是非常合理的！這會誤觸 `pasted`：
- 不寫 `_回.txt` 也不寫 `_usage.json`（等於白花錢沒記帳）；
- 回傳 `'pasted'` 導致 `fail += 1` → 寫出 `.stage_partial` → **`run_pipeline.py` 與 `run_all_books.py` 直接整批停止往下推進！**

## 二、中度 Bug（解析錯誤、正規化漏網、提示詞殘缺）

1. **`qwen_local.py` 的打包額度加成 `_pn` 在盲翻、審核、修訂全部失效**：
   第 424 行寫 `_unit = text.split('【本次待審單元】')[-1]`，接著 `.split('【前文背景')[0]`。
   但盲翻標題是 `【本次待譯單元】`，審核/修訂標題是 `【原文】`！找不到 `【本次待審單元】` 時，`split` 回傳全文，再切 `【前文背景` 前面，結果只剩下開頭 Prompt，**算出的 `_pn` 永遠是 `0`**（只有卷首第一段沒前文背景時才算得到）。
2. **`qwen_local.py` 的 `_split_col3` 若遇同欄寫在同一行會切錯**：
   第 381 行用 `j = out.find('\n', i)` 切出第 3 欄標題行。若模型遵守 `3. **修正後的譯文**：PASS_A_KEEP_A` 寫在同一行，整個 `PASS_A_KEEP_A`（或第一行譯文）會被留在 `head` 而不是 `col3`，導致 `_strip_dup_labels` 與 `_looks_pasted` 跳過第一行，且 `head + col3` 在行中多插一個換行。
3. **`norm.py` 的 `_depth` 跨行累計與簡繁轉換鎖死**：
   `_depth = 0` 宣告在 `for ln in text.split('\n'):` 迴圈外。在古籍標點裡，只要整段中有**任何一個未閉合的 `「` 或 `『`**，後面所有段落的 `_depth` 全程 `>= 1`，導致後面所有行的 `VAR_MAP`（包含簡轉繁 `问→問`、`这→這`、`说→說`）**全部罷工**！另外，把簡體字放進受 `_depth == 0` 限制的 `VAR_MAP`，也會讓模型打在 `「引文」` 內的簡體錯字漏改。
4. **`_strip_head_paren` 會誤刪正常譯文開頭的條目序號**：
   `mk_audit_materials.py`、`mk_revise_materials.py`、`build_a2.py` 的 `_strip_head_paren` 會無條件刪掉開頭任何一對 `（...）` 或 `(...)`。但提示詞又規定子條目用 `（一）（二）`、夾注保留圓括號。若某段譯文剛好以 `（一）...` 或原文夾注開頭（尤其當模型漏寫標籤或拆回時標籤在上一層），`（一）` 會被直接吃掉！建議只過濾含特定後設字眼（如 `註|按|說明|沿用|未改`）的括號。
5. **`col3` 正則漏掉 `**` 與 `build_a2.py` 誤切風險**：
   - `mk_audit` / `mk_revise` / `build_a2` 的 `col3` 正則在 `譯文` 後面寫 `[：:\s]*\n?`，但提示詞範例是 `3. **修正後的譯文**：`（`譯文` 後面有 `**`），導致主正則沒中，每次都退回 `rfind('修正後的譯文')`。
   - `build_a2.py` 處理 `REVISE` 回覆時先跑 `col3(_rt)`。但 `REVISE` 是純譯文輸出，萬一譯文內容裡恰好出現「修正後的譯文」六個字（例如譯某段談「修正經文」的句子時），`rfind` 會把前面整段譯文截掉！
6. **`materials_io.verdict()` 誤判風險**：
   - 若審核寫 `2. 【結論】：無 FIX，判 PASS`，正則抓到前面的 `FIX` 就直接判 `FIX`。
   - 若寫 `3. 【必改硬傷】：經逐句核對，本段無必改硬傷。`，因不以 `無`/`皆無` 等字開頭，`verdict()` 會把 `PASS` 翻盤成 `FIX`，白跑一次修訂。
7. **`local_corpus.py` 的潛在 `NameError` 與別名拆解遺漏**：
   - 第 191 行 `if per_book is None: per_book = rows if work else 2` 中的 `rows` 未定義（參數名稱是 `limit`）。
   - `_split_work(query)` 只認 `BOOKS | EXTRA.keys()`，不認 `ALIASES`。若模型搜 `query="婆沙 僧殘"` 而不填 `work`，`"婆沙"` 會被當成正文必含詞去搜而查無結果。
8. **提示詞本身的小問題**：
   - `mk_review_materials.py` 的 `get_prompt(False)`（文件 2.2）末尾有個沒接起來的殘缺病句：`「...科判動詞。含偷搬【記文】解釋進【疏文】、或【記文】原文無該欄則略去；或「銜接【記文】實詞須附原字」」`，且題號跳過 `3.`；`SYSTEM_PROMPT` 題號跳過 `4.`；`JUDGE_PROMPT` 題號跳過 `2.`。
   - 當 `NO_WEB=1` 時，`qwen_local.py` 的 `SYSTEM_PROMPT` 後段依然寫著 `web_search 1～2 次、web_fetch 1 次`，模型還是會花思考Token評估是否能網搜。
   - `mk_review_materials.py` 中，`業疏`/`戒疏` 若一組連續 `【疏】` 或 `【記】` 合計 >500 字（例如兩行各 300 字），paired 迴圈會跳過整組，接著 unpaired 迴圈把這兩行拆成兩個單段組，**失去了【疏】【記】雙向互核**；若 `【疏】` <40 字也會被拆散。

## 三、會造成大量成本／Token 浪費的地方

### 1. 最大浪費：「打包裁決 → 拆回原狀 → 逐段終審」（省前不省後）
在 `run_pipeline.py` 的 `packjudge` 中，你把 3,309 組《業疏》壓成 1,264 份（呼叫數 −62%），省了一大筆輸入與固定 prompt；**但緊接著 `do_split` 把它拆回 3,309 份，然後 `audit`（終審）又去跑 3,309 次獨立 API 請求！**
每次獨立請求都要重送：
- System prompt（~600 字）＋ Audit prompt（~450 字）＋ 前文 900 字 ＋ 後文 600 字 ＋ `xhigh` 思考 ＋ 工具輪次。
如果短段在 `packjudge` 後**不要急著拆回**，直接延續打包狀態跑 `audit` 與 `revise`，到 `final` 再一次拆回（就像你針對舊批次寫的 `pack_audit.py` + `pack_final.py` 那樣），終審階段可以再省下約 **50–60% 的輸入 Token 與呼叫數**。

### 2. 全程對「初譯（盲翻）」開 `xhigh` + `KEEP_THINKING=1`
文件第八節自己也寫到：「便宜模型洗一輪 → 高階模型挑錯終審」。但目前的 `run_all_books.py` 與 `run_pipeline.py` 裡，**盲翻、裁決、終審全部跑 `qwen4-max-preview` + `xhigh` + `preserve_thinking=True`**！
你實測 7.6 的數據已經證明：`xhigh` + `preserve_thinking` 一旦進多輪工具呼叫，平均單檔輸入暴衝到 **46,398 tokens**（一般檔的 3 倍，整批 74% 的輸入 Token 集中在那 16 檔）。
- 修掉前述 **Bug #1 (`own_text` 誤殺)** 後，多輪工具空轉就會大幅下降。
- **盲翻階段**其實可以改用 `effort=medium`（或較便宜的模型／關閉 `KEEP_THINKING`），把 `xhigh` + `KEEP_THINKING=1` 集中保留給 **Judge 與 Audit**，效益會好非常多。

### 3. `pack_judge.py` 兩項保守限制讓大量短組無法打包
- `if it['packed'] or len(it['bl']) > 1: continue`：**《業疏》《戒疏》只要是「疏＋記」雙欄組（就算疏 50 字＋記 50 字），一律拒絕打包**。其實雙欄短組在《業疏》《戒疏》佔比極高，允許總原文 ≤300 字的雙欄組一起打包（或至少讓 `pack_audit` 邏輯套用過來），能再砍掉大量呼叫。
- `mk_review_materials.py` 單欄書（《資持記》《行事鈔》等共 6,600+ 組）打包上限寫 `acc < 220`、最多 4 段，比 `業疏` 未配對段的 `acc < 460`、最多 10 段保守很多；其中《資持記》4,182 組若放寬到 350–400 字，可再省約 25–35% 盲翻請求。

### 4. `pack_judge.py` 要求 `REVISED` 全量抄寫未改動段落（浪費輸出 Token）
`RULE` 規定只要同包內 6 段中有 1 段要改，模型必須把另外 **5 段沒改動的全文照抄一遍**。輸出 Token 單價通常比輸入貴 3–5 倍，這樣既燒輸出費，又增加模型抄漏或格式跑掉導致 `do_split` 失敗的風險。
如果改成 `REVISED` **只輸出有改動的 `[n]` 段落**，由 `do_split` 自動從 `pack` 原檔把沒列出的 `[n]` 用譯本甲補回，輸出 Token 與拆回失敗率都會大幅下降。

### 5. `web_search` 缺乏防呆機制與快取 Key 不一致
對比你幫 `local_search` 做的防呆（`memo` 去重、`remaining` 計數、最後一次 `notice`），`web_search` 這邊完全沒做：
- 沒給 `remaining` 和 `notice`，模型容易在額度用完時再叫一次白白多送一輪歷史。
- 沒有同一組內的查詢去重（`memo`）。
- Tool schema 寫 `預設 10`，但函數寫 `int(rows or 15)`，快取 key 把 `cnt`（`10` vs `15`）編進去了，模型傳 `10` 跟沒傳 `rows` 會被當成不同快取，對同一關鍵詞向 DeepSeek 付兩次費。

### 6. `local_corpus.py` 每次查詢線性掃描 41.9 萬行（CPU 與併發瓶頸）
`find()` 每次都 `for idx, r in enumerate(LINES):` 掃描全部 419,185 行。當查詢詞是「比丘」「受戒」這類每本書都有的詞時，40 個執行緒同時在純 Python 裡跑 40 萬次迴圈並互搶 GIL，不僅拉長整體執行時間，也增加記憶體與 CPU 負荷。改為按書分索引（`BOOK_LINES[book]`）或啟動時建立簡易的 2-gram 倒排索引，掃描量會從 40 萬行降到數百行。
