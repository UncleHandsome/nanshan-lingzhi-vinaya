## 一、自我矛盾與規格衝突（最優先處理）

### 1. `JUDGE_PROMPT` 與 `mk_judge_materials.py` 對「原打包段」指令打架（有漏段風險）
* **現象**：`JUDGE_PROMPT` 寫：「並依材料附的【分段要求】或【併批裁決要求】決定『全列』或『只列改動段』」。
* **衝突點**：
  * `pack_judge.py` 的 `【併批裁決要求】` 明確寫「只列有改動的段，未列段自動沿用譯本甲」。
  * 但 `mk_judge_materials.py` 面對原本在切分階段就打包的短段（如《尼鈔》119 個打包組），所附的 `【分段要求】` 只寫「請保留 `[1][2]…` 編號逐條對應，勿合併、增減條數」，**漏了明確寫出「須全列」**。
  * 如果模型誤以為「打包段都可以只列改動段」而略過沒改的 `[1]`，因為這類材料沒經過 `pack_judge.py` 的 `do_split()` 補回譯本甲，`build_a2.py` 會直接把缺少 `[1]` 的殘缺譯文當成最終定稿！
* **建議**：`mk_judge_materials.py` 的 `【分段要求】` 必須明確加上「**第 3 欄須全數逐條完整輸出，不得省略未改條目**」；更好的是直接分清兩個詞彙（原打包叫「多條併段」，裁前打包叫「併批裁決」），不要混用。

### 2. `pack_judge.py` 的 `【輸出標籤】` 與雙欄結構互咬
* **現象**：`pack_judge.py` 注入 `【輸出標籤】疏文／記文（標籤寫在該欄最前一次，其下逐條列 [n]）`，強制把整包按「先全部【疏文】[1][2]…，再全部【記文】[1][2]…」排列。
* **問題**：對 LLM 來說，材料原文是「`[1]` 疏＋記、`[2]` 疏＋記」，輸出卻要它**跨段轉置矩陣**變成「疏 `[1][2]`、記 `[1][2]`」。這也是為什麼你們必須在 `do_split()` 裡寫幾十行 `_pending`、`_trail`、`_mtail` 來搶救模型寫成 `[1] 【疏文】…【記文】…` 的情況。
* **建議**：雙欄打包不如直接順從模型直覺，規定**以 `[n]` 為一級節點**（`[n]` 下寫 `【疏文】…【記文】…`），反而更不容易跳號或串欄。

### 3. `REVISE_PROMPT`「禁止寫理由括號」vs「允許駁回」＋無標題切除死角
* **現象**：`REVISE_PROMPT` 原則 3 要求模型在清單明顯錯誤時「駁回該項（勿寫理由、按語或說明括號）」。
* **矛盾點**：整個系統裡**只有 `REVISE_PROMPT` 叫它駁回，卻沒給它【駁回說明】欄位**。實務上模型很難做完判斷後完全忍住不解釋（你們在 `build_a2.py` 第 155 行特地寫 regex 去刪 `（按：…）（駁回：…）` 就是證據）。
* **程式死角**：在 `build_a2.py` 第 144 行，若這段剛好沒有標籤（或單欄打包），程式會先手動在開頭加上 `【鈔文】\n`，再進 `_plain_revise()` 找第一個 `【鈔文】` 截斷。這會讓模型寫在最前面的任何駁回廢話（如 `經核對，第2條駁回，修訂如下：`）**被夾在 `【鈔文】` 後面，直接寫進定稿**！
* **建議**：要嘛讓 `REVISE_PROMPT` 固定輸出兩欄（`【修訂處置】` 簡記修改或駁回理由 ＋ `【修訂後譯文】`），讓 `build_a2.py` 乾淨取第 2 欄（完全杜絕說明混入正文，也解決模型硬憋理由導致亂改的問題）；若想省輸出 token，至少 `build_a2.py` 應先抽離標籤與廢話再補標籤。

### 4. `STYLE_SPEC` 第 4 條「引號雙體例」邊界未定＋重複 3 次
* **現象**：`STYLE_SPEC` 第 4 條同時允許兩種完全相反的引號用法：
  * 用法 A：「僅逐字完整對譯……才以「……」包圍，**引號內放白話譯文**」
  * 用法 B：「先引原文再白話者，**引號內只放原詞或原句，白話解釋置於引號外**」
* **矛盾／張力**：
  1. **沒寫何時該用 A、何時該用 B**。結果盲翻用 A、舊譯用 B，裁決和終審就會為此打架；你們甚至不得不在 `AUDIT_PROMPT` 第 1 條特地加一條超長的補丁括號（`註：注疏體例中先引原文一句、再以白話解釋，不視為雙譯疊詞……`）來幫用法 B 解套。
  2. 此外，`STYLE_SPEC` 第 1 條的「保留文言例外清單」只列了「被訓釋原詞」，**沒列「先引原文再白話的整句引文」**，兩條字面不夠對齊。
  3. 同一段裡「改（為）無引號（間接）轉述」這句話**重複講了 3 次**（第 2 句「古人節略引述…」、第 4 句「屬大意撮述…」、第 6 句「無法確認是否逐字引用…」）。
* **建議**：明確定義分界（例如：**凡引文附有訓釋／解說者用 B；儀軌與短警句直接譯入行文者用 A；其餘節略或疑為改寫者，一律改無引號轉述**），並把重複三次的轉述條件合併為一句。

### 5. `STYLE_SPEC` 第 5 條「薩婆多」的誘發性說明 & `norm.py` 隱性規則
* **問題 A**：`STYLE_SPEC` 第 5 條寫「薩婆多屬律＝《十誦律》……正文一律保留原稱《善見》《薩婆多》，不補「律」字、不展開全稱」。對**譯者/審核**而言，既然規定正文一律保留原稱，就不該在 `STYLE_SPEC` 裡寫出「薩婆多屬律＝《十誦律》」（放在 `SYSTEM_PROMPT` 第 3 條供查證判讀就夠了），寫在體例裡反而會誘發模型把《薩婆多》改寫成《十誦律》。
* **問題 B（提示詞沒寫、程式卻強制改）**：
  * `norm.py` 會把 `《…篇／品／章／節／門／犍度》` 強制轉成單書名號 `〈…〉`，但**全套提示詞隻字未提單書名號 `〈〉`**。
  * `norm.py` 和 `merge_long.py` 都認行首的 `問：` / `答：`，但提示詞**沒規定「問曰／答曰」統一譯為「問：／答：」**，導致行內問答或不同角色（「有人問：」vs「問曰：」）無法統一。

### 6. `LOCAL_SCHEMAS` 誘導誤填 `work`
* **現象**：你們在 7.8 節發現 28%（4,662 次）`local_search` 查無，92% 是因為模型亂填 `work`。
* **衝突點**：`LOCAL_SCHEMAS` 的工具說明第一句寫「`（37 部；work 可寫簡稱或全稱）`」，卻**沒列出哪 37 部**，又寫「僅於確知…時填書名」。這在語用上反而是在鼓勵模型去「猜」書名並填入 `work`。且一旦猜錯的那本書剛好有 1 筆不相干的命中，就不會觸發 `qwen_local.py` 的「查無跨書放寬」！
* **建議**：把 `work` 描述直接改強硬：**「預設留空（全庫檢索已包含這 37 部並會分層取樣，且回傳結果會標示所屬部別）；僅在全庫命中過多且已明確知道欲核對《四分律》《行事鈔》《業疏》《戒疏》等確切書名時才填。」**（或直接把 37 部精簡名表放進工具說明，反正只有 ~180 字）。

## 二、過度針對（Overfitting）／補丁感太重的條款

這套提示詞明顯能看出「每修一次錯題就往規則裡塞半句話」的演進痕跡。以下條款過度貼合個別特例，建議泛化或抽離：

1. **`JI_NOTE`（《資持記》專屬，每次帶 260 字）**：
   * 裡面寫「**不可一律解作《隨機羯磨》**」——《資持記》根本不是《隨機羯磨》的記，本來就不會去套《隨機羯磨》，這明顯是怕模型把《業疏》的習慣帶過來而打的反向補丁。改成正面規定「『文』須依《行事鈔》該處所引或上下脈絡判讀（或指律文、戒本、羯磨文、諸部引文或本鈔下文）」更自然。
   * 裡面還寫「**《濟緣記》『疏』指《業疏》、《行宗記》『疏』指《戒疏》，記中『鈔云』不得解作《四分律》**」——這是檢索跨書參照時才用得到的常識，只有《資持記》帶這句、其他書卻沒有，略顯錯位。建議移去 `SYSTEM_PROMPT` 第 3 條典籍簡稱旁（一句話帶過三記的互稱即可）。
   * 「**記中單稱「《序》」者，依脈絡辨明為《事鈔序》或本記序**」——非常針對特定卷的個例補丁，全書 4,182 組每組都重送一次，性價比偏低。

2. **`REVISE_PROMPT` 原則 1 的特例舉例**：
   * 「不得刪去原譯正確之主詞、**出處限定（如「《四分律》的律文」）**或條件」——明顯針對某次修訂漏掉「《四分律》的律文」所加，保留「不得刪去原譯正確之主詞、出處限定或條件」即可，不必帶例子。

3. **`SHUJI_CTX` 與 `SHUJI_NOTE` 的雙書捆綁與補丁**：
   * 無論跑《業疏》還是《戒疏》，**每一組都同時送「《業疏》指《隨機羯磨》，《戒疏》指《含注戒本》」**！但程式明明在組材料時就已經確定這份是《業疏》還是《戒疏》了，沒必要讓 3,309 組業疏一直讀戒疏的規則，反之亦然。
   * 「『文云／故文云』若緊承前引《四分律》等他典，須先核對出處，嚴禁未查即套《隨機羯磨》」——對單欄／疏記是有效防呆（L5 07 組教訓），但可收斂為「遇『文云／故文云』須先核對前引典籍，勿盲套母本」，既省字數又同時覆蓋《戒疏》的《含注戒本》（目前這句寫死「嚴禁未查即套《隨機羯磨》」，對《戒疏》來說反而套錯書名了！）。

4. **過度密集的「禁止語」稀釋模型注意力**：
   * 粗算單份盲翻材料裡「勿／不得／嚴禁／切勿／禁止／不可／禁用」高達 **30 處以上**。模型在高壓負面禁令下容易發生兩極反應：要嘛過度保守（不敢補承前主詞，違反遮蔽反讀），要嘛在長文裡漏掉核心義理檢查（如 7.4 節 06 組全鏈漏檢）。

## 三、過度精簡（或遺漏關鍵資訊）的地方

1. **`REVISE_PROMPT` 體例縮水導致「修一條壞一條」的風險**
   * `REVISE_PROMPT` 為了省 token 沒注入完整 `STYLE_SPEC`，只在原則 4 用一句話摘要，卻叫它在原則 3「方向過粗時自擬精確修法」。
   * **實質遺漏清單**（與 `STYLE_SPEC` 對比）：
     * 漏了例外項：**人地書名、戒名、儀軌稱謂、法數、「第X篇：……」〔末不加句號〕、無確據之「某某反」**（原則 4 只留了 `某甲／古度量／未定〔補字〕／〔疑作X〕／專名與被訓釋原詞`）。
     * 漏了「**先引原文再白話者，引號內只放原詞或原句，白話解釋置於引號外**」與「**條目序數用一、二、（一）（二）**」。
     * 漏了「**《善見》《薩婆多》保留原稱、不補律字**」（只寫「他律簡稱補律字，簡稱不展開全稱」，容易與前句衝突）。
   * 若終審正好挑了上述這幾類錯（例如「戒名誤加引號」除外有寫，但「誤改法數」「引文與白話混入引號」「條目序數錯」），修訂階段手上卻沒有完整條文可參照。

2. **`AUDIT_PROMPT` 缺少「反讀檢查」的顯性輸出卡控**
   * 終審要求做「2. 遮蔽原文反讀」，但 `【逐句簡核】` 只要求核對「主客施受、關鍵動詞、條件／否定界限與專詞實義」。實務上 LLM 寫完逐句字面核對後，很容易忘記用「純白話讀者視角」重讀一次全段是否缺主語或指代懸空。建議在 `【逐句簡核】` 最後加一句強迫輸出：「末句附一句『反讀通順無歧義』或點出斷裂處」。

3. **`AUDIT_PROMPT` 的「勿代寫完整替換句」與「修正方向」拿捏模糊**
   * 要求「勿代寫完整替換句」卻又要填 `｜修正方向：……`，模型常為了避嫌把「修正方向」寫得很空泛（例如「依律義明確指出受事對象」），結果迫使 `REVISE_PROMPT` 再補一段「修正方向過粗時應自擬精確修法」。其實**允許針對該單句給出「建議改為：……」或極精簡的局部詞組替換，反而比要求「寫抽象方向」更不易誤改，也更省修訂階段的思考與檢索 token**。

4. **長文切片語氣豁免與 `LOGIC_CHECKLIST` 的位置衝突**
   * `mk_split_blind.py` 把「續段銜接優先於語法自足（勿補主詞、勿強加句號）」的 `LONG_TAIL` 放在 `LOGIC_CHECKLIST` 的後面，但 `STYLE_SPEC`（第一句就是「譯為語法自足之現代繁體白話」）又緊接在 `LONG_TAIL` 後面！被前後兩側的「語法自足」夾擊，模型很容易忽略那兩行小字。

## 四、是否太臃腫？（Token 結構與 Prefix Caching 診斷）

從絕對長度看，這不是一般聊天機器人的幾句話，而是一個**單份請求前導 Prompt 就達 ~2,000–2,300 中文字（約 2,500–3,200 tokens）** 的重型系統：

### 1. 同文義跨欄位重複嚴重
以**盲翻**為例，同一份材料裡：
* 「**不要把前後背景／記文譯入正文**」講了 **4–5 次**（導語 1 次、原則一 1 次、`{shuji_rule}` 1 次、材料裡各背景標題 2–3 次）。
* 「**背景截斷用中性泛稱、勿臆補**」在原則 1 講完，原則 2 又講「依原文語法與律脈翻譯，勿自行補述」。
* `STYLE_SPEC` 第 4 條「改無引號轉述」講了 **3 次**。
* `BLIND_PROMPT`／`JUDGE_PROMPT` 的打包指令：即使在佔絕大多數的**非打包單段**材料上，模型每次也都要讀 `JUDGE_PROMPT` 裡一長段「打包段每條前加 `[n]`，並依材料附的【分段要求】或【併批裁決要求】…」。

### 2. 最傷成本與緩存的結構問題：**變動變數放在靜態長文前面！**
看一下你們 4 支主力 Prompt 的組裝順序：
* `BLIND_PROMPT`：`{scope}`（第 1 行就變）、`{book_ctx}`、`{shuji_rule}` → 然後才是固定不變的 **1,060 字** `{logic_checklist}` + `{style_spec}`！
* `JUDGE_PROMPT`：`{book_note}`（會依單/雙欄變）→ 然後才是固定不變的 `{logic_checklist}` + `{style_spec}`！
* `AUDIT_PROMPT`：`{dual_note}`、`{long_note}`、`{book_note}` → 然後才是固定不變的 `{logic_checklist}` + `{style_spec}`！

在支援自動前綴快取（Prompt Prefix Caching，如 Qwen / DeepSeek）的 API 上，只要前面任何一個 `{book_note}` 或 `{scope}` 從雙欄切換成單欄、或出現 `{long_note}`，後面佔 Prompt 70% 長度的 `LOGIC_CHECKLIST` + `STYLE_SPEC` 就**無法命中前綴快取**！
👉 **只要把完全靜態的 `{logic_checklist}` 和 `{style_spec}` 移到 `SYSTEM_PROMPT` 末尾或 User Prompt 最前面（所有 `{變數}` 之前）**，這 1,060 字在整個幾萬筆的批次裡就可以享受極高的 KV Cache 命中率，既降延遲又省 input 費用，而且「體例總則在前、本段任務參數在後」對模型注意力也更友好。

## 五、立即可做的瘦身與重構建議清單（不傷精準度）

如果不想大幅打掉重來（畢竟 L7 已經驗證過高穩定度），可以做以下**低風險、高收益**的整理：

1. **先改順序（零風險省 Cache）**：將 `{logic_checklist}` 與 `{style_spec}` 抽到每個任務 prompt 的最開頭（在所有 `{book_note}`/`{scope}`/`{dual_note}`/`{long_note}` 之前），甚至考慮讓靜態體例固定不變。
